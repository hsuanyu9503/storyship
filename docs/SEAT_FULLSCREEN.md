# 學生座號、確認加入後進入全螢幕、全黑遮罩、打字與全螢幕（2026-11-26）

保留既有課程流程與定稿文案。這份文件取代 [`FONT_AND_WRAP.md`](FONT_AND_WRAP.md) 第 1 節（舊的「回到全螢幕」浮動提示）。

## 1. 學生打字時退出全螢幕：重現與原因

### 重現（修正前的 main `7c22cba`，Playwright Chromium 153 headless，觸控模擬 1024×768）

在全螢幕中依序操作，每一步都以 `document.fullscreenElement` 檢查：

| 操作 | 結果 |
|---|---|
| 03 點分類名稱欄位、英文鍵入 | 仍在全螢幕 |
| 03 注音組字＋選字「故事」（CDP `Input.imeSetComposition`／`insertText`）、移動游標刪字 | 仍在全螢幕，文字與游標正確 |
| 教師切換專注模式（同步重畫） | 仍在全螢幕，輸入框焦點與文字保留 |
| 可視區域縮成 1024×420（模擬虛擬鍵盤）、恢復 | 仍在全螢幕 |
| Enter 完成輸入、視窗 `blur` 事件 | 仍在全螢幕 |
| 04 分類名稱與共同特色：注音、鍵入、等同步 3 秒、點其他地方 | 仍在全螢幕 |

整段只有一次 `fullscreenchange`（進入）。

### 原因

* **程式本身不會讓瀏覽器退出全螢幕。** 程式沒有呼叫 `exitFullscreen`。全螢幕元素是 `<html>`，重畫時不會被替換。程式也沒有監聽 `resize`、`blur`、`visibilitychange` 來判斷全螢幕。輸入框在同步時保留焦點與內容。
* 因此課堂上看到的「打字就退出全螢幕」，是**裝置或瀏覽器在虛擬鍵盤或文字輸入時由系統退出全螢幕**，不是程式重畫或焦點造成。
  * 這個環境沒有實體平板，**無法確認是哪一種裝置、哪一個系統行為**。
  * 我查了 iPadOS Safari（WebKit）的全螢幕原始碼，看到的部分沒有「打字就退出」的規則，所以不推測具體原因。
  * 請回報發生問題的裝置型號、系統版本與瀏覽器，以便實機確認。
* 修正前的版本還有一個加重問題的地方：退出後，「回到全螢幕」提示會直接出現在打字的畫面上。如果裝置每次打字都會退出，學生就會卡在「回到全螢幕 → 一打字又退出」的循環。

### 處理方式（不論是哪一種裝置）

* 全螢幕狀態**只看瀏覽器的實際狀態**：`document.fullscreenElement`、`webkitFullscreenElement`、`fullscreenchange` 事件。視窗縮小、虛擬鍵盤出現、頁面暫時失去焦點，都不會被判為退出。
* 退出全螢幕時，如果**焦點在文字欄位**，就延後顯示黑色遮罩：
  * 學生可以繼續注音組字、選字、修改，輸入框不會失去焦點，游標位置也不變。
  * 畫面上方顯示不擋操作的小提示「完成輸入後，請回到全螢幕」，旁邊有按鈕。
  * 學生離開文字欄位後（點其他地方、收起鍵盤並點別處、按 Enter 完成分類名稱），內容先照常儲存，然後才顯示黑色遮罩。
* 所以就算裝置每次打字都會退出，學生也一定能完成輸入，不會形成無法作答的循環。代價是每次編輯完要按一次「回到全螢幕」。
* 如果實機確認某台裝置每次打字都會被系統退出，可行的方案有：
  1. 改用不會退出的瀏覽器或裝置，例如 Android 平板上的 Chrome。
  2. 接受「編輯完按一次回到全螢幕」。
  3. 只對該類裝置在打字期間不要求全螢幕（需要再決定）。

## 2. 座號

### 學生端

* 選組畫面依序是：「座號（必填）」→ 組別（點選後以底色標示）→「加入」→ 確認視窗「確認加入第 N 組？座號 N 號。」→「確認加入」。
* 座號欄位設定 `inputmode="numeric"`（數字鍵盤）、`pattern="[0-9]*"`，最多 3 位數，接受 1～999 的整數。全形數字也接受（「０５」→ 5）。
* 錯誤訊息：
  * 空白：「請先輸入座號。」
  * 不是數字：「座號只能填數字，例如 5。」
  * 0 或超出範圍：「座號請輸入 1～999 的整數，例如 5。」
  * 未選組別：「請選擇你的組別。」
* 出錯時，輸入內容與已選組別都保留，焦點回到座號欄位。
* 加入失敗時（網路中斷、老師暫停加入、該組已滿），座號與組別保留，學生可以重試。這台裝置上次輸入的座號會記在本機，重新整理後會自動填入。
* 加入後，學生端標題列顯示「第 2 組・12 號」。

### 資料庫與權限

* 新增 `participants.seat_no int`，有範圍檢查 `participants_seat_no_range`（null 或 1～999）。舊資料為 null，升級時不修改任何既有資料。
* 學生識別方式不變，仍是裝置憑證雜湊 `token_hash`。座號只用於顯示。原本的 `seat_label`（組內加入順序）保留，教師換組時仍會重新編號，但座號不變。
* 學生只能透過 `student_join`（security definer，以裝置憑證識別）寫入自己的座號：
  * anon 不能直接讀寫 `participants`。
  * 教師（authenticated）只能讀取自己場次的 `seat_no`，不能直接改寫。
  * 這些權限都由 `tests/db/tests.sql` 與 `verify.sql` 第 18 項檢查。
* `student_join(p_code, p_token, p_group_number, p_seat_no int default null)`：
  * 新加入：保存座號。
  * 已加入的裝置再次加入（重新整理、清掉紀錄後重來）：恢復原身分，**保留原座號**。如果原本沒有座號（舊資料），補上這次輸入的座號。
  * 被教師移出後重新加入：使用這次輸入的座號。
  * 座號超出範圍：`INVALID_SEAT`，不建立學生紀錄。
  * 舊版前端只帶三個參數時仍可加入，座號為 null（部署期間，瀏覽器快取的舊頁面也能用）。學生端畫面本身一定要求填座號。
* `student_state` 的 `me` 增加 `seat_no`。重新整理、斷線重連、教師端刷新後，都從資料庫取得同一個座號。

### 教師端顯示（`js/lib/seat.js` 的 `seatText`）

* 有座號時顯示「5 號」「12 號」。成員依座號排序，沒有座號的排在後面。
* 舊資料沒有座號時顯示「未填座號（組內第 N 位）」。如果連加入順序都沒有，顯示「未填座號」。不會出現空白、undefined 或 null。
* 套用的地方：
  * 連線管理（各組成員、移出確認）
  * 02 各組加入狀態
  * 03 個人分類成員表與「查看」標題
  * 04 小組進度表的連線欄
* 資料庫還沒升級時（沒有 `seat_no` 欄位），教師端改讀舊欄位，仍可使用，座號一律顯示「未填座號」。

### 同場次重複座號：目前行為與建議（請確認）

* **目前行為**：允許重複。兩位學生都能加入，教師端各自顯示「12 號」，例如第 2 組「5 號、12 號」、第 6 組「12 號」。學生端不會提示。
* **建議**：維持允許加入，不在伺服器端拒絕，並在教師端把重複的座號標示「座號重複」，由老師口頭確認。
  * 不建議拒絕的原因：打錯座號的學生會占用別人的號碼，讓正確的學生無法加入，課堂上更難處理。
  * 是否加上教師端標示，請你決定後我再實作。

## 3. 確認加入後直接進入全螢幕

* 正常流程是：輸入座號 → 選擇組別 → 加入 → **確認加入（進入全螢幕）** → 活動畫面。
* 「確認加入」按鈕的點擊事件中，**先同步呼叫 `requestFullscreen()`**，再送出加入請求，最後等兩者都完成（`js/lib/dom.js` 的 `buttons[].onSelect`）。
  * 這樣不會因為等網路回應，而失去瀏覽器要求的使用者操作授權。
* 加入失敗：已進入全螢幕也沒關係（還沒加入，不要求全螢幕），座號與組別保留，學生可以重試。
* 加入成功、但全螢幕請求被拒絕：保留已加入的身分，直接顯示黑色遮罩，下方加一行「瀏覽器沒有允許全螢幕，請再按一次「回到全螢幕」。」，學生按按鈕重試。
* 原本 02 的「進入探索模式」按鈕已移除，加入時就進入探索模式。02 畫面改顯示「已進入探索模式（全螢幕），請等待老師開始。」。

## 4. 退出全螢幕時的全黑遮罩

* 學生加入後（包括重新整理、斷線重連後恢復身分），只要瀏覽器實際不在全螢幕，就顯示不透明的黑色遮罩，中間只有「請回到全螢幕，繼續活動」與白色大按鈕「回到全螢幕」。
* 遮罩是 `<dialog>` 以 `showModal()` 開啟：
  * 放在瀏覽器最上層，蓋住整個可視區域，包括活動畫面、卡片、標題列與閱讀卡等對話框。
  * 背景頁面變成 inert，滑鼠、觸控、Tab、Esc 都不能操作背景。Esc 也不能關閉遮罩。
  * 如果之後又開啟其他對話框，遮罩會重新回到最上層。
* 按鈕高 76px、最小寬 300px，可用觸控、滑鼠、鍵盤（焦點在按鈕上按 Enter 或空白鍵）操作。只有 `fullscreenchange` 確認進入全螢幕後，遮罩才關閉。
* 遮罩只建立一次，事件監聽在模組載入時只註冊一次，反覆退出／返回不會累積。測試有確認畫面上永遠只有一個遮罩。
* 遮罩不重畫下面的畫面，作答、卡片位置、閱讀卡翻面狀態、尚未送出的文字都保留。同步照常進行，教師切換環節或結束活動後，學生返回就看到最新畫面。
* 請求失敗：
  * 遮罩顯示原因，學生可以重試。
  * 連續失敗兩次後，改為「仍無法進入全螢幕。請舉手告訴老師；需要時可先以一般畫面繼續。」，並出現「先以一般畫面繼續」，避免學生被困住。之後一旦成功進入全螢幕，就恢復正常規則。
* 瀏覽器完全不支援全螢幕（例如 iPhone 的 Safari，或 `fullscreenEnabled` 為 false）：
  * 不顯示遮罩，以免學生被困在無法解除的畫面。
  * 上方顯示一次「這台裝置的瀏覽器不支援全螢幕，活動將以一般畫面進行。」，活動照常。
  * 建議課堂改用 iPad 或 Android 平板的瀏覽器。
* 被教師移出、回到選組畫面時，不再要求全螢幕。

## 5. 資料庫升級步驟（不在正式資料庫執行；由管理者執行）

1. **先升級資料庫，再更新網站。** 舊版網站與新版資料庫相容：舊前端以三個參數呼叫 `student_join` 仍可使用。新版教師端在資料庫尚未升級時也能顯示，只是座號都是「未填座號」。
2. 在 Supabase SQL Editor 執行 **`supabase/upgrade/upgrade.sql`**（單一交易、可重複執行）。結果表格 18 列的 `ok` 都應為 `true`。第 18 項檢查：
   * 座號欄位與範圍檢查存在
   * 新版加入函式存在且學生可執行
   * 舊的三參數版本已移除
   * 教師可讀、不可改座號
   * 學生不能讀座號
3. 網站合併到 `main` 並部署後，所有裝置重新整理。
4. 不需要回復腳本：`seat_no` 欄位保留不影響舊版網站，退回舊版網站即可。

## 6. 實際測試

* 瀏覽器：Playwright Chromium 153（headless），Linux（容器）。**全部是瀏覽器模擬，沒有實體裝置測試。**
  * 觸控用 Playwright 的 `hasTouch` 模擬。
  * 中文輸入法用 CDP `Input.imeSetComposition` 模擬組字、`Input.insertText` 模擬選字。
  * 虛擬鍵盤用 CDP 縮小可視區域模擬。
  * 「Esc 或系統退出全螢幕」用 `document.exitFullscreen()` 模擬。
  * 請求被拒絕：改寫 `requestFullscreen` 讓它回傳失敗。
  * 不支援全螢幕：移除 API、讓 `fullscreenEnabled` 為 false。
* 尺寸：學生 1024×768（觸控），教師 1366×1024。
* `tests/e2e/seat_fullscreen.js`：從正常學生入口與教師入口操作，共 91 項以上，涵蓋：
  * 座號表單的錯誤訊息與保留
  * 確認加入後進入全螢幕
  * 教師端同組座號（依座號排序）
  * 03／04 各輸入欄位的組字、選字、修改
  * 可視區域縮小與失去焦點時不顯示遮罩
  * 打字中退出時延後遮罩，返回後繼續輸入，伺服器保存
  * 開著閱讀卡（背面）時連續退出三次：以鍵盤、觸控、滑鼠返回，背景不能點、不能 Tab、不能 Esc，翻面狀態保留，頁面沒有重新載入
  * 遮罩期間教師切換到 04、結束活動
  * 重新整理、斷線重連
  * 加入失敗（網路中斷、暫停加入）
  * 全螢幕被拒絕（重試、先以一般畫面繼續）
  * 不支援全螢幕
  * 舊資料沒有座號、重複座號、伺服器範圍檢查、恢復時保留座號、anon 與教師都不能直接改座號
  * 教師端 02／03／04 的成員清單
* `tests/db/tests.sql`：座號 20 項（範圍、恢復、舊資料補座號、換組不變、移出後重新加入、權限、跨教師隔離）。
* `tests/db/upgrade_bundle.sh` 第 11 項：從目前的 main（`7c22cba`），加上 03 進行中、學生沒有座號的場次升級：
  * 資料不變，18 項全過
  * 既有學生可繼續操作，新學生可帶座號加入
  * 重複執行不改座號
* `tests/unit/seat.test.mjs`：座號輸入與顯示。

### 尚未驗證

* 實體平板：iPad（Safari）、Android 平板（Chrome、Samsung Internet）、Chromebook、Windows 觸控筆電。
  * 包括實際的虛擬鍵盤、注音／倉頡／手寫輸入法、系統手勢退出全螢幕，以及「打字時被系統退出全螢幕」的具體裝置與重現條件。
* 實機上的使用者操作授權時效：例如 Safari 是否允許在「確認加入」點擊中、關閉確認視窗前請求全螢幕。程式在同一個點擊事件中同步請求，這是標準做法，但沒有在 Safari 上驗證。
* Firefox、Safari、Edge 桌面版。
* 真正的 Supabase 雲端專案（只在本機 PostgreSQL＋模擬 API 驗證；沒有在正式資料庫執行 SQL）。
