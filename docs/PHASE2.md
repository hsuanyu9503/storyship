## 4. 資料模型與一致性

沿用 Phase 1 的 JSON 草稿結構（`personal_boards.data`）：

```json
{"categories":[{"id":"c1","no":1,"name":"會魔法"}],"placements":{"<故事 uuid>":"c1"}}
```

| 規格要求 | 對應欄位／機制 |
|---|---|
| 場次 ID、匿名學生 ID | `personal_boards.session_id`、`participant_id`（學生只以裝置憑證雜湊識別） |
| 小組 ID | 由 `participants.group_id` 取得（個人資料不複製小組欄位，換組也不影響個人成果） |
| 分類群組、名稱、顯示順序 | `data.categories` 陣列順序＝顯示順序；`no` 為暫時名稱編號 |
| 每張故事的歸屬 | `data.placements`（物件，一張卡只能有一個值，結構上不可能重複歸屬） |
| 編輯版本、最後更新時間 | `rev`、`updated_at` |
| 是否完成提交 | `submitted_at` |
| 是否鎖定 | 由本場次是否已有 `personal_snapshots` 推導（`app.personal_closed`）；場次層級，返回 03、晚到的裝置、離線後重連都同樣被拒絕 |
| 快照：原場次、原學生、完整內容、版本、建立時間、完成狀態 | `personal_snapshots.session_id`、`participant_id`、`data`、`board_rev`、`taken_at`、`is_complete`（＋`submitted`） |

**為什麼用 JSON 而不是多列**：個人分類只有學生本人會寫入，不需要多人同時修改不同欄位，
整份資料搭配版本號即可防止舊資料覆蓋新資料；伺服器 `app.normalize_personal` 檢查格式、故事是否屬於本場素材、分類是否存在。
小組分類（Phase 3）則因為多人同時操作，Phase 1 已設計成多列＋各欄位版本號＋操作鎖。兩者是**完全不同的資料表**。

**儲存一致性**：

| 風險 | 處理 |
|---|---|
| 快速連續移動，較早的請求晚到 | 前端一次只送一個儲存請求；新變更等上一個完成後才送最新版本 |
| 文字延遲儲存覆蓋最新名稱 | 名稱輸入 0.7 秒 debounce；輸入法組字中不送出；離開欄位、按 Enter 立即送出；永遠送出「目前最新」的整份資料 |
| 同一學生兩個分頁 | 每次儲存帶 `p_expected_rev`；版本不符時伺服器回傳最新資料，前端改用伺服器資料並提示一次 |
| 重新整理讀到舊版本 | 所有資料從伺服器讀取；未送達的變更存在 localStorage（含基準版本），只有伺服器版本仍等於基準版本時才補送 |
| 離線裝置在教師結束後重連 | 伺服器拒絕（`PERSONAL_LOCKED`／`NOT_AVAILABLE`），前端丟棄本機暫存，改顯示已鎖定成果 |
| 提交時最後一次修改尚未送達 | 先等待所有變更經伺服器確認，再以同一版本號提交；伺服器確認後才顯示「已完成」 |
| 重複點擊提交 | 按鈕在處理中停用；伺服器對已提交者直接回傳成功，不產生第二份資料 |
| 教師切換環節時同時收到學生儲存 | `FOR SHARE`／`FOR UPDATE` 互斥（見第 0 節 #2） |

**權限**：學生（anon）不能直接讀任何資料表，只能透過 RPC 讀寫**自己**的草稿（以裝置憑證判斷）；
同組學生也沒有任何 RPC 能取得他人的個人分類。教師以 RLS 只讀自己場次的資料。投影端只讀教師公開的投影內容，其中不含個人分類。

## 5. 學生端操作設計

* **橫向**：左側「尚未分類」約 40%、右側「我的分類」約 60%，兩欄各自捲動；「完成個人分類」固定在右下，不隨分類增加被推出畫面。
* **直向**（或窄螢幕）：上下配置（未分類在上，分類在下），各自捲動，不需縮放。
* **閱讀 vs. 移動**：點卡片內容＝閱讀；卡片右側的「⠿ 移動」把手專門負責移動：
  * 拖曳把手（滑鼠或手指）到分類、到「尚未分類」、或到「＋新增分類」；把手設定 `touch-action: none`，其他地方可正常捲動。
  * 點一下把手＝選取，上方出現提示，再點目標分類（或「尚未分類」、「＋新增分類並放入」）完成移動。
* **點按判斷**以 pointer 事件處理：平板瀏覽器在觸控後有時不送出 click，或把 click 送到剛重畫的元素上，
  因此「選取」與「放入」都在 pointerup 判斷，並忽略同一位置緊接著的那一次 click（避免誤開閱讀視窗）。
* **命名**：直接在分類上輸入，空白時顯示淡色的「分類 N」；支援中文輸入法組字、最多 30 字。
* **刪除分類**：分類內有故事時先確認，故事回到尚未分類。
* **提示**：正常儲存時不顯示任何訊息；只有儲存超過 1.5 秒、離線、儲存失敗、資料在另一個畫面更新、暫停、鎖定時才提示。

| 13 | 尚有故事未分類／有分類未命名時按完成 | 顯示「還有 N 張故事尚未分類。」／「請為分類 N 取一個名稱。」 |
| 14 | 全部完成並命名後按完成 | 顯示「✓ 已完成個人分類」；教師端「已完成個人分類」人數增加 |
| 15 | 學生按「繼續修改」再完成 | 可再修改並重新完成 |
| 16 | 教師展開某組 → 查看 | 看到該學生的分類；投影畫面不變 |
| 17 | 教師按「暫停個人分類」→「恢復個人分類」 | 暫停時學生不能移動但可閱讀；恢復後繼續 |
| 18 | 教師按「結束個人分類，進入第四環節」 | 顯示未完成人數；選「返回等待」不變；確認後進入 04 |
| 19 | 學生在 04 按「查看我的個人分類」 | 唯讀顯示自己的分類；未完成者標示未完成 |
| 20 | 教師按「← 上一環節」回到 03 | 學生端顯示「老師已結束個人分類，你的成果已保存」，無法修改 |
| 21 | 橫向／直向旋轉平板 | 兩種方向都能完整操作，不需縮放 |

## 8. 已知限制與尚待驗證

* **尚待實機驗證**：iPad Safari／Android Chrome 的手指拖曳手感、虛擬鍵盤與中文輸入法、長按與捲動的互動、
  正式 Supabase 的 Realtime（本機以輪詢驗證；Realtime 失敗時仍會在 3 秒內同步）。
* 個人分類一旦結束（建立快照）即無法由教師重新開放；若需要此功能可在後續版本加入「重新開放個人分類」（會刪除快照，需教師確認）。
* 若教師跳過 03（例如從 02 直接到 04），同樣會建立（空白的）個人快照並鎖定。
* 名稱輸入後 0.7 秒內教師就結束個人分類，或學生在儲存途中關閉頁面，最後這一筆變更可能不會進入快照
  （快照只採用伺服器已確認的資料，這是規格要求的行為）。
* 鍵盤操作（Tab／Enter）可以選取故事，但目標分類目前只支援滑鼠或觸控點選。
* 投影端 03 目前不顯示時間提醒（規格為「可保留」，未實作）。
