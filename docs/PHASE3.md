## 4. 多人即時同步的實作

```
學生操作 ──► 本機佇列（一次送一個） ──► 單一目標 RPC（伺服器驗證身分／組別／環節／暫停／提交／鎖／版本）
   │                                              │
   └─ 畫面＝伺服器資料＋尚未確認的操作            └─ 寫入成功 → board_rev +1 → realtime.send('group:<小組>')
                                                                                  │
其他組員 ◄── 重新讀取 student_group_board（Realtime 通知，或每 2 秒輪詢）◄──────────┘
```

* **伺服器是唯一真實來源**：Realtime 訊息不含資料，只是「有變更」的通知；漏收、重複、亂序都不影響結果，因為收到後一律重新讀取。
* **不會畫面回溯**：讀到的 `board_rev` 比目前已知的舊時直接忽略。
* **不整份覆蓋**：每個操作只針對一個目標（`group_add_category`、`group_move_card`、`group_update_category`、
  `group_delete_category`、`group_submit`），伺服器以該目標的版本號判斷。不同故事卡、不同欄位的操作可同時成功。
* **樂觀顯示與校正**：畫面立即顯示本機操作；伺服器拒絕（`STALE`、`LOCKED`、`NOT_FOUND`、`DELETED`）時丟棄該操作並重新讀取，
  畫面回到伺服器資料，必要時顯示一句提示（例如「組員剛剛移動了「故事 C」，已更新為最新位置。」）。
  尚未確認的成果不會被顯示為已提交：「已完成」只在伺服器回報小組狀態為 `submitted` 時出現。
* **訂閱管理**：每位學生只有兩個頻道（`lesson:<場次>`、`group:<小組>`）；工作區只在換場次或換組時重建，
  資料更新只做局部重畫，不會累積重複訂閱。
* **局部更新**：分類框以 id 保留同一個 DOM 節點；正在輸入的欄位不被遠端資料改寫；按壓或拖曳故事卡時延後套用遠端更新；
  閱讀視窗、個人面板、捲動位置不受同步影響。

## 5. 操作衝突與資料版本

| 情境 | 處理 | 驗證 |
|---|---|---|
| 兩人同時移動同一張卡 | 先選取的人取得卡片鎖，另一人顯示「組員操作中」；即使同時送出，伺服器依序處理，後到的回傳 `LOCKED`／`STALE` | race、e2e |
| 兩人同時移動不同卡 | 各自成功（每張卡獨立版本） | concurrency、e2e |
| 兩人同時新增分類 | 小組列鎖定後依序取得編號，全部保留 | race（8 個同時）、e2e |
| 兩人改同一名稱／理由 | 欄位鎖（`name:<id>`／`reason:<id>`）；他人顯示「組員輸入中…」；舊版本 `STALE` | db、e2e |
| 同一分類：一人改名稱、一人改理由 | 欄位級，不互相阻擋 | e2e |
| 移入他人正在刪除的分類 | 依序處理：先刪除→移動 `NOT_FOUND`；先移動→刪除時故事回到未分類 | race（隨機先後 6 次） |
| 修改已刪除的分類 | `NOT_FOUND`，不重建 | db |
| 刪除他人正在輸入的分類 | `LOCKED`（按鈕也會停用） | db、e2e |
| 取得鎖後斷線 | 15 秒逾時；其他人即可取得；斷線者之後的舊版本寫入 `STALE` | db（Phase 1）、e2e |
| 重複送達 | 新增：同 id 回傳原結果；移動／改字：已是相同結果回傳 `unchanged`；刪除：`NOT_FOUND` 視為完成 | db |
| 舊的回應晚到 | `board_rev` 比較，舊的忽略 | 設計＋e2e 收斂檢查 |
| 教師暫停／結束時同時有學生操作 | 鎖定順序保證：進行中的先完成並被快照包含；之後的被拒絕 | race 情境 1、2、6 |
| 兩人同時提交 | 一份快照，另一人 `ALREADY_SUBMITTED` | race 情境 3、六組並行 |
| 提交時他人仍在輸入 | `EDITING`，提示「組員正在輸入或移動故事，請等他完成後再提交」 | db、e2e |

**操作鎖策略**：鎖存在 `group_locks(group_id, target, participant_id, expires_at)`（小組隸屬場次，因此範圍含場次、小組、目標）。
有效期 15 秒，持有期間每 5 秒續約；每位學生同時只持有一個鎖；移動完成、取消選取、離開欄位時釋放；提交、環節切換時清除該組所有鎖。
移動與改字時若他人持有鎖一律拒絕；自己未持有鎖但無人持有時仍允許（版本號保證不會覆蓋），以減少點按延遲。

## 8. 已知限制與尚待驗證

* **尚待驗證**：正式 Supabase 的 Realtime（本機以輪詢驗證）；實體平板的手指拖曳與捲動、虛擬鍵盤、中文輸入法；
  實際教室 Wi-Fi 下 20～30 人同時使用的延遲。
* Realtime 頻道為公開頻道：知道小組 id 的人只能收到「有變更」訊號（不含內容），最多讓各端多讀取一次。
* 學生輸入文字有約 0.8 秒的延遲儲存；教師在這 0.8 秒內結束共同分類時，最後幾個字不會進入快照（快照只採用伺服器已確認的資料）。
* 不提供撤銷：刪除分類前會確認，刪除後故事回到未分類，可手動再整理（避免把整份成果回復到舊版本而清除他人的操作）。
* 教師端進度每 5～10 秒更新一次（非 Realtime 時）。
* 每位學生同時只持有一個操作鎖；一人不能同時拖曳故事又在別的欄位輸入（平板上也不會這樣操作）。
* 離線期間尚未送出的操作會在恢復連線後重送；若期間被組員改動，該操作會被拒絕並以伺服器資料為準（文字會提示原本輸入的內容）。

## 9. Phase 4 可使用的小組成果資料

**取得各組目前有效的最新成果**（教師身分，RLS 只會回傳自己場次的資料）：

```sql
select distinct on (group_id) *
  from public.group_snapshots
 where session_id = :session
 order by group_id, created_at desc;
```

`group_snapshots` 欄位：`id`、`group_id`、`session_id`、`kind`（`submitted`＝學生正式提交／`locked`＝教師結束保存）、
`is_complete`（只有學生正式提交且完整才為 true）、`board_rev`（成果版本）、`created_at`、`data`：

```json
{
  "categories": [
    {"id": "…", "order": 1, "label_no": 1, "name": "會魔法的故事", "reason": "主角都有神奇的力量",
     "cards": ["<故事 id>", "…"]}
  ],
  "placements": [{"card_id": "<故事 id>", "category_id": "…或 null"}],
  "unplaced": ["<故事 id>"]
}
```

* 只含有故事的分類，依分類順序排列；名稱、理由已去除前後空白。
* 重新開放再提交會新增一筆，舊的提交快照永久保留（可顯示版本歷程）。
* 學生原始個人分類：`personal_snapshots`（`data`、`is_complete`、`submitted`、`board_rev`、`taken_at`）。
* 故事素材：`story_cards`（`id`、`title`、`summary`、`detail`、`image_url`、`sort_order`）。
* Phase 4 的 05 應只讀快照（不讀可變動的 `group_categories`／`group_placements`），並由教師端把「要公開的部分」組成投影資料，
  沿用 Phase 1 的「投影只讀 `session_state.projection`」原則。
